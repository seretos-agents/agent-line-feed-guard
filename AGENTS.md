# agent-line-feed-guard

Hook-only plugin — no binary, no MCP server. `hooks/hooks.json` wires three events to a single script (`scripts/line-feed-guard-hook.mjs`) that converts CRLF to LF in the files Claude Code parses: every file under a project's `.claude/**` (excluding Claude-internal churn dirs and vendored trees), `.claude/*.json`, root `CLAUDE.md` / `AGENTS.md` / `CLAUDE.local.md` / `.mcp.json`, and — narrowly — the user config dir. It also ships two skills: `line-feed-guard` (preventive — the rule, before the agent writes) and `scan` (on-demand sweep, `--scan` CLI mode).

## Contracts an agent won't infer from the tree

- **Release is orphan-branch + marketplace dispatch.** `release.yml` (manual: Actions → release → `version=X.Y.Z`) stamps the version into both manifests, force-pushes an orphan `release` branch holding only install-ready files, tags `agent-line-feed-guard--vX.Y.Z`, and POSTs a dispatch (`category: hook`) to BOTH `seretos-agents/modular-software-factory-staging` (lands straight to main, no review) and `seretos-agents/modular-software-factory` (opens a review PR). `main` and `release` share no history.
- **Required secret:** `MARKETPLACE_DISPATCH_TOKEN` — fine-grained PAT, `Contents: RW` + `Pull requests: RW` on both `seretos-agents/modular-software-factory` and `seretos-agents/modular-software-factory-staging`.
- **`assets/icon.png` and `description.md` are release artifacts, not just repo files.** The dispatch payload sends `raw.githubusercontent.com/${repo}/${TAG}/…` URLs for both, so they must live on the orphan `release` branch at the tagged commit — that is why `release.yml`'s stage step copies them. Replace the placeholder icon and fill in `description.md`'s Key Features before cutting v0.0.1.
- **Release notes are generated from `main`, via a `src/<TAG>` marker tag — and that marker needs a one-time human bootstrap for whatever the previous release already is.** The orphan `release` commit shares no history with `main`, so `--generate-notes`/`--notes-start-tag` on the orphan tag have nothing to walk and publish an empty body. `release.yml` instead pushes an ordinary (non-orphan) tag `src/<TAG>` at `main`'s tip on every release, and asks `releases/generate-notes` to walk `main`'s history between `src/<TAG>` and `src/<PREV_TAG>` — two commits that do share history. `.github/scripts/release-preflight.sh` runs before any side effect and refuses to proceed if a resolved previous release (`.github/scripts/prev-release-tag.sh`, `<plugin>--v*` tags only, strict SemVer precedence, never `src/*`) has no `src/<PREV_TAG>` marker yet — there is no automatic backfill, because creating a ref at a historical commit needs human credentials (`GITHUB_TOKEN` can only be trusted to push a ref whose tree is the default-branch tip, which a historical commit generally is not). Bootstrap it once, manually, per the exact commands pre-flight prints when it fails on this:
  1. read `head_sha` from the Actions run of `<PREV_TAG>`
  2. `git tag src/<PREV_TAG> <head_sha>`
  3. `git push origin src/<PREV_TAG>`
  Do this once for whatever tag pre-flight names as the missing previous marker before the next release; it fails in the same way for `agent-line-feed-guard--v0.0.1` until that bootstrap has been done.
- **The published GitHub Release's body is what the marketplace dispatch's `changelog` gets, never a second/raw `generate-notes` call.** After `gh release create` publishes with `--notes-file`, the dispatch step reads the body back with `gh release view "$TAG" --json body --jq .body` and forwards it as `.github/scripts/marketplace-payload.sh`'s optional `CHANGELOG` env var, which is omitted from the payload entirely (not sent as an empty string) when empty.

## Why the design looks like this

- **Event confidence is tiered, and the tiers are load-bearing.**
  - *Tier 1* — `PostToolUse` and `SessionStart`. Publicly documented, and the plugin's guarantees rest on them.
  - *Tier 2* — `FileChanged`. Verified present in the shipped Claude Code binary (2.1.222) but publicly undocumented. It catches CRLF from writes no tool call made: an external editor, `git checkout`, another terminal. It is deliberately built so that if it silently stops firing, nothing breaks — the next `SessionStart` or `Bash` call catches the same file. Do not move any guarantee onto it.
- **`FileChanged` must be configured without a `matcher`.** The binary derives watch paths from each `FileChanged` hook's `matcher` split on `|` and joined to cwd — a matcher would register junk watch paths. Both code paths handle an absent matcher (it then matches everything), so omitting it is correct and intended.
- **`FileChanged` cannot talk to the model.** Its `hookSpecificOutput` union member carries only `watchPaths` — there is no `additionalContext`. Top-level `systemMessage` is its only channel, which is why that branch emits `systemMessage` alone and no `hookSpecificOutput` at all.
- **`hookEventName` must match the firing event exactly.** The hook runner throws `Hook returned incorrect event name` otherwise. This is why the three branches never share an output builder.
- **There is deliberately no `git status` and no mtime window.** The scope is not "what changed" — it is a statically known set of a few dozen small files. A git spawn costs 20–150 ms on Windows plus an index refresh, more than reading the whole scope (1–3 ms); it never reports gitignored files such as `.claude/settings.local.json`; it does not work outside a working tree; and it answers the wrong question, since only the bytes on disk say what has CRLF *now*. Dropping it also removes the entire mtime/state apparatus and every loop risk from the hook's own writes. **Do not reintroduce it as an "optimisation" — it is a pessimisation here.**
- **Idempotence is the loop-prevention mechanism.** `stripCrlf` returns `null` when there is no CRLF and the caller writes only on a non-null result, so a second pass is a no-op with empty stdout. The `FileChanged` self-trigger therefore terminates in one step.
- **Writes are plain `writeFileSync`, not temp-file + rename — on purpose.** A rename replaces the inode: it would break symlink identity (this workspace symlinks `mcp-test/plugins/*` into `plugins/`), drop explicit ACLs, and fail with `EPERM`/`EBUSY` on Windows when an editor holds a share-deny handle. The files are well under 100 KB, so the truncate window is microseconds.
- **The two root kinds have deliberately different scopes, and re-unifying them is a regression.** A *project* root scans its whole `.claude/**`, minus `PROJECT_EXCLUDED_TOP_DIRS` (`projects`, `file-history`, `shell-snapshots`, `todos`, `statsig`, `plugins` — first segment only) and `VENDOR_DIRS` (`node_modules`, `.git`, `.venv`, `venv`, `__pycache__` — any depth). The *user config dir* is scanned narrowly and watched even more narrowly: only `{agents,skills,commands,hooks}` (`CONFIG_SCOPE_SUBDIRS`), top-level `*.json` and `CLAUDE.md` — never `projects/`, `file-history/`, `shell-snapshots/` or `plugins/`, which churn constantly and would make both the scan and the chokidar watcher expensive. `CONFIG_SCOPE_SUBDIRS` governs the config kind **only**; the project kind spells its four priority dirs locally. The scan bound that keeps this plugin viable inside Unity projects and `node_modules` trees is unchanged: it descends only into `.claude/`, which neither of those lives under. (The config-side *watch* list in `watchPathsFor` really is three — `agents`, `skills`, `commands` — and stays three; that is a separate, narrower list from `CONFIG_SCOPE_SUBDIRS`, which has always had four.)
- **The project walk is two-phase, and `isAgentFile` has a known, accepted false positive.** Phase 1 walks the four harness-critical dirs (`agents`, `skills`, `commands`, `hooks`) first, so they cannot be starved by `MAX_FILES` if an unexpected subtree sits under `.claude/`, and so their pre-widening `MAX_DEPTH` origin is preserved (depth counted from e.g. `agents/`, not from `.claude/`). Phase 2 sweeps the rest of `.claude/` in one readdir, with depth counted from `.claude/` itself. Separately: `isAgentFile` matches any `/agents/` path segment, so a repair under e.g. `.claude/tools/agents/` will claim a subagent was fixed even though it wasn't one — accepted, because tightening it to a literal `.claude/agents/` prefix would break user-level agents under a redirected `CLAUDE_CONFIG_DIR`, which have no `.claude` segment at all.
- **UTF-16 is reported but never transcoded.** PowerShell 5.1's `Out-File` and `>` default to UTF-16LE, which Claude Code also cannot read — same symptom, different cause. Surfacing it is cheap; transcoding is out of scope for a line-ending guard and would be a much riskier write.
- **`systemMessage` is spent only on `agents/**` fixes.** Agent definitions are read once at startup, so a silent failure there survives the whole session and is worth interrupting the user for. Everything else stays agent-facing. That is the entire noise budget.
- **Unverified, and the messages reflect it:** whether SessionStart's `reloadSkills` also re-reads the *subagent* registry. Its docstring names only "skill and command directories". The plugin therefore promises nothing and tells the user to restart.

## Testing

`scripts/line-feed-guard-hook.test.mjs` — plain Node, no framework, no dependencies, `fs.mkdtempSync` per test, exit 0 = pass.

**Every end-to-end test must inject `CLAUDE_CONFIG_DIR` and `LINE_FEED_GUARD_STATE_DIR` into a sandbox** (`sandboxEnv()` does this). Without it the hook enumerates — and rewrites — the real `~/.claude` tree. The symlink-recursion test skips itself when symlink creation is unprivileged, which is the normal case on Windows without Developer Mode.

`.github/scripts/release-scripts.test.mjs` — same plain-Node shape, exercising the real `prev-release-tag.sh`, `release-preflight.sh` and `marketplace-payload.sh` through `spawnSync` (a faked `gh` stub on `PATH` answers the pre-flight tests' existence checks; the pre-flight tests also run inside a real `git init` temp repo so `main_sha` is real). `lint.yml`'s "Run release script tests" step runs it on every PR; it needs `bash`, `jq` and `git` on `PATH`.
